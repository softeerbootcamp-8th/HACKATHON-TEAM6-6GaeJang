# 태은 주석 총정리 — pot 도메인 설계 근거

- 목적: `pot` 패키지 코드에서 **덜어낸 "왜"를 잃지 않기 위한 보관 문서**다.
  - 코드에는 "이게 뭐 하는 코드인지"와 없으면 사고가 나는 한 줄만 남겼다.
  - 배경·대안 비교·트레이드오프는 전부 여기로 옮겼다.
- 배경: `pot`의 주석 비율이 26%였는데 `chat`·`member`·`auth`는 11~12%였다.
  - 같은 저장소에서 한 패키지만 설명이 3배 두꺼우면 리뷰어가 "여기만 자신이 없나"로 읽는다.
- 읽는 방법: 코드에서 판단이 막히면 해당 클래스 절을 찾아 읽는다. 심사·발표 질문 대비 자료로도 이 문서를 쓴다.

---

## 1. 도메인 한 줄 요약

- 배달팟(`Pot`) — 총대가 열고 근거리 이웃이 참여해 배달을 같이 시키고 나누는 모집 글.
- 흐름 — 총대가 팟 생성(+채팅방 자동 생성) → 이웃이 메뉴와 함께 참여 → 총대가 주문·수령 → 나눔 완료.
- 팟과 채팅방은 **팟 → 채팅 단방향**이다. 채팅은 팟을 모른다.

---

## 2. Pot (엔티티)

### 좌표를 DECIMAL 두 컬럼으로 둔 이유

- 홈의 300m 반경 조회 때문에 좌표가 필수다. 만날 장소 텍스트만으로는 거리 계산이 불가능하다.
- MySQL `POINT` + spatial index 대신 `DECIMAL(10,7)` 두 컬럼을 썼다.
  - 해커톤 규모(팟 수백 건)에서는 바운딩 박스 필터 + 하버사인이 충분하다.
  - JPA 매핑이 단순하고, h2 테스트에서도 같은 쿼리가 그대로 돈다.
- 소수점 7자리는 약 1cm 단위다. 300m 판정에는 과분하지만 반올림 고민을 없애준다.

### 인덱스 두 개의 근거

- `idx_pots_lat_lng (latitude, longitude)` — 홈 목록에서 좌표 바운딩 박스로 후보를 줄이는 것이 가장 큰 절감이다.
- `idx_pots_status_deadline (status, deadline)` — 전체 목록은 "살아 있는 팟 중 마감 전"만 노출하므로 두 컬럼을 함께 탄다.

### hostId 를 `@ManyToOne Member` 로 걸지 않은 이유

- 회원을 **별도 애그리거트**로 취급한다. 팟에서 회원을 타고 들어갈 일이 없고, 팟과 회원의 수명도 독립이다.
- 목록 카드에 총대 정보가 나가지 않으므로 조회 편의가 필요 없다.
- 화면에 필요한 닉네임은 서비스가 `memberId`를 모아 한 번에 벌크 조회해 붙인다.
- 주의 — LAZY 프록시 자체가 N+1은 아니다. 프록시를 반복 초기화할 때 추가 SELECT가 나가면서 N+1이 된다.
  - 그래서 "프록시가 무서워서"가 아니라 "애그리거트 경계"가 진짜 이유다.

### FK 제약이 없는 점 (심사 대비 답변)

- `PotMember.potId` / `memberId`는 단순 `Long`이라 Hibernate가 FK DDL을 만들지 않는다.
  - DB 수준에서는 존재하지 않는 팟·회원을 가리키는 행이 이론상 가능하다.
- 그런데 고아 행을 만드는 코드 경로가 없다.
  - `pots`는 하드 삭제하지 않는다 — 완료는 `status = DONE` 전이일 뿐이다.
  - `Member`는 soft delete다 — 행이 남는다.
  - `potId`는 항상 `findPot()`을 통과한 값, `memberId`는 인증에서 온 값이다.
- 정합성 보장 수단 — 애플리케이션 검증 + `uk_pot_members_pot_member` unique 제약 + 참여/나가기를 한 트랜잭션에 묶는 것.
- 지금 `@ManyToOne`으로 전환하지 않은 이유
  - MySQL InnoDB는 자식 행 INSERT 시 부모 행에 공유 락(S lock)을 잡는다. `pot_members` INSERT마다 `pots` 행에 락이 붙는다.
  - 참여 동시성을 `@Version` 낙관적 락으로 풀고 통합 테스트까지 세워둔 상태라, 마감 전에 락 동작을 바꾸는 변경은 위험하다.
  - DDL로만 FK를 붙이는 대안은 더 나쁘다 — `ddl-auto: update`가 FK를 만들어주지 않고 마이그레이션 도구도 없어 환경별로 스키마가 갈린다.
- 결론 — 해커톤 후 `PotMember → Pot`만 `@ManyToOne(LAZY)`로 전환한다. `Pot → List<PotMember>` 양방향은 만들지 않는다(목록 조회에서 실제로 N+1을 만든다).

### chatRoomId

- 프론트가 "총대에게 메뉴 전달하기" 이후 어디로 이동할지 판단하는 값이다.
- nullable인 이유가 둘이다.
  - 채팅방 id는 팟이 저장돼야 알 수 있어 INSERT 시점에는 없다.
  - 채팅 연동 전에 만들어진 기존 팟이 null로 남아 있다.
- 단방향으로만 둔다(`ChatRoom`은 팟을 모른다).
  - 팟이 `DONE`이 되어 목록에서 사라진 뒤에도 방은 살아 있어야 한다. 팟 상태 변화가 채팅 조회로 새는 통로를 만들지 않는다.
  - 채팅방에서 팟 정보가 필요하면 이 컬럼을 거꾸로 탄다(`findByChatRoomId`).
- `linkChatRoom()`을 빌더로 받지 않은 이유 — 방 이름에 팟 정보(가게명)가 들어가서 팟이 먼저 저장돼야 한다. 통로를 둘로 두면 어느 쪽이 정본인지 흐려진다.
- 재할당을 막는 이유 — 방을 갈아치우면 이전 방에 남은 참여자와 메시지가 고아가 된다.
  - 정상 흐름에서 두 번 호출될 수 없으므로 도메인 예외가 아니라 `IllegalStateException`(프로그래밍 오류)으로 던진다.

### meetingPlace / meetingRoadAddress / meetingJibunAddress 를 셋 다 두는 이유

- `meetingPlace` — 화면에 한 줄만 보여줄 때 쓰는 표시용 주소. `Member.address`와 같은 자리이고, 총대가 가입 때와 같은 지도 화면에서 핀을 찍어 만든다.
- `meetingRoadAddress` — 카카오 역지오코딩의 도로명 결과. `meetingPlace`와 겹칠 수 있는데도 따로 두는 이유는 좌표만 있는 산·공터처럼 도로명이 없는 지점에서 `meetingPlace`가 지번으로 채워지기 때문이다.
- `meetingJibunAddress` — 도로명을 모르는 사람에게 주는 보조 값.
- 뒤 두 개가 nullable인 이유는 이 필드가 붙기 전에 만들어진 팟이 null로 남기 때문이다.

### currentMemberCount 를 컬럼으로 들고 있는 이유

- 목록 카드가 "2/4"를 그리는데, 팟마다 `count(*)` 쿼리를 날리면 목록 크기만큼 쿼리가 늘어난다(N+1).
- 대신 이 컬럼과 실제 `pot_members` 행 수가 어긋나지 않게 **참여/나가기를 한 트랜잭션에서 같이 움직인다.**
- 동시 참여로 정원을 넘기는 것은 `@Version` 낙관적 락이 막는다.
- 생성 시 1에서 시작한다 — 총대는 항상 첫 참여자다. 이 불변 규칙은 빌더 밖으로 내보내지 않는다.

### join() / leave() 를 setter 대신 둔 이유 (PR #59)

- 이전에는 `increaseMemberCount()` / `decreaseMemberCount()`가 사실상 setter였다.
  - "참여자 수는 0 이상 capacity 이하"라는 불변식을 `Pot`이 아니라 `PotService`만 알고 있었다(빈약한 도메인 모델).
- `join()` — 정원이 찼으면 거부.
- `leave()` — 0 이하 감소 거부 + ACTIVE 동안의 이탈 이력(`hasMemberLeft`)을 함께 기록.
  - 두 변경을 한 메서드로 묶은 이유는 **누락 방지**다. 전에는 `recordMemberLeft()`를 빼먹어도 컴파일이 되고 총대 경험치 판정만 조용히 틀어졌다.
  - 완료 후 나가기는 경험치 판정과 무관해 이력을 남기지 않는다.
- 예외 타입을 `IllegalStateException`으로 둔 이유
  - 사용자용 판정(`POT_FULL`, `POT_RECRUITMENT_CANNOT_SHRINK`)은 `PotService`에 **그대로 남겼다.** 검증을 옮긴 게 아니라 한 겹 더 얹은 것이다.
  - 같은 조건이라도 책임 주체가 다르다 — 정원 초과 참여 시도는 사용자의 잘못이고, 검증 없이 `pot.join()`을 부르는 것은 개발자의 잘못이다.
  - 그래서 엔티티 쪽은 400이 아니라 500으로 드러나야 한다.

### hasMemberLeft / countsAsHostExperience

- `hasMemberLeft` — 팟이 ACTIVE인 동안 누군가 나간 적이 있는지.
  - 총대는 완료 전엔 나갈 수 없으므로 이 시점의 "누군가"는 항상 참여자다.
  - 완료 시 총대만 남아 있어도 이 값이 true면 과거에 참여자가 있었다는 뜻이다.
- `countsAsHostExperience` — "총대 N회" 배지에 이 팟을 셀지 여부.
  - `complete()` 시점에 딱 한 번 계산해 고정한다. 완료 후 참여자·총대가 나가서 `currentMemberCount`가 줄어도 이미 확정된 경험치가 흔들리면 안 된다.
  - 판정식 — `currentMemberCount > 1 || hasMemberLeft`.
  - **주의** — 벌크 UPDATE(`PotRepository.completeAbandoned`)는 이 메서드를 타지 않으므로 같은 식을 쿼리의 `case when`에도 복제해 뒀다. 한쪽만 고치면 자동완료된 팟의 배지가 틀어진다.

### 검증을 엔티티가 아니라 서비스가 하는 이유

- `complete()`의 총대 권한·현재 상태 검증은 서비스에 있다. 엔티티는 전이만 수행한다.
- 검증을 엔티티에 두면 마감 후 5시간 경과 일괄 전이(벌크 UPDATE)에서 규칙이 두 곳으로 갈라진다.

### update() 가 부분 수정을 지원하지 않는 이유

- 화면이 생성 폼과 같은 전체 폼이어서 항상 모든 값을 다시 보내온다.
- 부분 수정(null이면 유지)을 섞으면 "지웠다"와 "안 보냈다"를 구분할 수 없어진다.
- `status` / `currentMemberCount` / `chatRoomId`는 건드리지 않는다. 수정은 모집 조건을 다시 쓰는 것이지 진행 상태를 되돌리는 것이 아니다.

### hasOnlyHost() — 참여자가 있으면 수정을 막는 이유

- 이미 전달된 메뉴가 다른 가게 기준이 된다.
- 송금할 계좌와 받으러 갈 장소가 참여자 모르게 바뀐다.
- 잘못된 정보로 들어온 사람이 있으면 총대가 채팅으로 정리하는 쪽이 값을 조용히 갈아치우는 것보다 낫다.

### expandRecruitment() — 늘리는 방향만 여는 이유

- 참여자가 이미 있어도 열려 있는 **유일한** 변경 경로다.
- 늘리는 방향은 참여자에게 손해가 없다 — 자리가 더 생기고 시간이 더 생긴다.
- 반대로 정원을 줄이면 이미 들어온 사람이 정원 밖으로 밀리고, 마감을 당기면 참여자가 기대한 시간표가 짧아진다.
- 같은 값으로 다시 호출해도 문제없다(멱등). 화면이 두 값을 함께 보내므로 한쪽만 바꾸면 다른 쪽은 현재 값 그대로 들어온다.

## 3. PotStatus

- 상태가 답하는 질문은 하나다 — **"이 팟이 아직 살아 있는가".**
- enum 이름이 그대로 응답 JSON에 나가므로 프론트와의 계약이다. 이름을 바꾸면 프론트가 깨진다.
- "모집 중인가"를 상태로 두지 않은 이유 — 성질이 다른 두 축이 있고 그중 하나만 저장해야 한다.
  - **살아 있는가** — 이벤트로 바뀐다(총대가 완료를 누른다, 유예 시간이 지난다). 계산할 수 없으니 컬럼으로 저장한다. 그게 이 enum이다.
  - **지금 참여할 수 있는가** — `deadline > now` 비교로 언제든 계산된다. 컬럼으로 두면 시각이 흐를 때마다 누군가 갱신해야 하고, 갱신 전까지 두 값이 어긋난다.
- 그래서 **마감시간이 지난 팟도 `ACTIVE`다.** 살아는 있고 새로 못 들어올 뿐이다.
  - 참여 가능 여부는 응답의 `isDeadlinePassed` 계산 필드로 내려준다.
- `ACTIVE` — 참여자·총대 목록에 계속 뜬다. 마감 후는 주문·입금·수령 구간이고 참여자에게는 그때 팟 정보(계좌, 만날 장소)가 오히려 필요하다. 달라지는 건 전체 목록에서 빠진다는 것뿐이다.
- `DONE` — 참여자를 포함한 모두의 목록에서 사라진다. 채팅방은 남아 하단 채팅 탭에서 계속 볼 수 있다. 총대의 완료 버튼 또는 마감 + 5시간 경과로 전이된다.

## 4. PotMember

### 총대도 한 행으로 들어가는 이유

- 홈 목록이 "내가 연 팟"과 "참여중인 팟"을 같은 방식으로 찾아야 한다.
- 총대만 `Pot.hostId`로, 나머지만 이 테이블로 찾게 하면 조회가 두 갈래가 된다.
- 총대 여부는 `Pot.isHost(memberId)`로 구분하고, 이 테이블은 "이 팟에 속한 사람 전부"를 뜻한다.

### unique(pot_id, member_id)

- 중복 참여의 **최종 방어선**이다. 서비스가 먼저 확인하지만 같은 사람이 참여 버튼을 두 번 빠르게 눌렀을 때는 DB 제약만 막을 수 있다.
- 제약 이름을 `PotMember.UK_POT_MEMBER` 상수로 뽑은 이유 — `@UniqueConstraint(name = ...)`와 `PotService`의 예외 번역이 같은 값을 쓰게 하려고.
  - 문자열을 양쪽에 따로 적으면 이름을 바꿨을 때 번역이 조용히 안 걸려 중복 참여가 500으로 나간다.
- `idx_pot_members_member (member_id)` — "내가 속한 팟 전부"가 홈 진입마다 실행되므로 단독 조회를 인덱스로 받친다.

### menuContent / menuPrice

- 참여할 때 입력한 메뉴·옵션 자유 텍스트. 총대가 배달앱에 그대로 옮겨 적는 값이다.
- 서버가 구조화하지 않는 이유 — 가게마다 옵션 구조가 달라 표준 스키마를 만들 수 없다. 총대가 읽고 주문할 수 있으면 충분하다.
- `menuPrice`는 총대의 최소주문금액 충족 판단에 쓰인다.
- **총대 자신의 행은 둘 다 null이다** — 팟을 만들 때는 메뉴를 입력하지 않는다.
- 그래서 팩토리가 둘이다 — `PotMember.host(...)`는 메뉴 없이, `PotMember.join(...)`은 메뉴 없이는 만들 수 없다(메뉴 입력이 곧 참여).

## 5. Geo

### 거리 판정을 두 단계로 나눈 이유

1. `boxAround()`로 위경도 사각형을 만들어 `idx_pots_lat_lng` 인덱스로 후보를 줄인다.
2. 후보에만 `distanceMeters()`로 정확한 구면 거리를 계산해 반경 밖을 버린다.

- 사각형만 쓰면 모서리가 반경을 넘는다 — 정사각형 대각선 = 변 × √2이므로 300m 요청에 최대 424m가 섞인다.
- 구면 거리만 쓰면 계산식이 컬럼을 감싸 인덱스를 못 타고 풀스캔한다.
- 그래서 둘을 겹쳐 쓴다.

### 상수

- `EARTH_RADIUS_METERS = 6_371_008.8` — 지구 평균 반지름, WGS84 기준.
- `METERS_PER_LATITUDE_DEGREE = 111_320.0` — 위도 1도의 거리. 경선을 따라가므로 위치와 무관하게 거의 일정하다.
- `COORDINATE_SCALE = 7` — 좌표 컬럼이 `DECIMAL(10,7)`이라 비교값도 같은 스케일로 맞춘다.

### 경도 보정과 극 방어

- 경도 1도의 거리는 고위도로 갈수록 줄어든다(경선 간격이 좁아진다).
- `cos(위도)`로 나눠 보정하지 않으면 고위도에서 사각형이 실제 반경보다 좁아져 반경 안의 팟을 놓친다.
- `Math.max(cos, 1e-6)` — 극 근처에서 cos가 0에 수렴해 폭이 발산하는 것을 막는다. 한국 위도에서는 걸리지 않는 방어 코드다.

### 하버사인을 쓰는 이유

- 평면 피타고라스를 쓰면 위도에 따라 달라지는 경도 1도의 실제 거리를 반영하지 못한다.
- 300m 규모에서 오차가 크지는 않지만 보정 없이 쓰면 동서 방향 거리가 과대평가된다.

## 6. PotRepository

### completeAbandoned — 자동 완료를 벌크 UPDATE로 둔 이유

- 안 하면 참여자 목록에 끝난 팟이 영구히 쌓인다. 내 섹션은 마감시간을 보지 않기 때문에 `DONE`이 되는 것 말고는 사라질 방법이 없다.

- 팟마다 엔티티를 읽어 전이시키면 목록 크기만큼 UPDATE가 나가므로 한 문장으로 끝낸다.
- `clearAutomatically = true` — 벌크 UPDATE는 영속성 컨텍스트를 우회하므로 1차 캐시를 비워 바로 뒤 조회가 낡은 상태를 읽지 않게 한다.
- `countsAsHostExperience` 계산식을 `case when`으로 복제해 `Pot.complete()`와 맞춰뒀다(위 2절 참고).

### findChatRoomIdsAbandoned — UPDATE 직전에 따로 조회하는 이유

- 벌크 UPDATE는 엔티티를 읽지 않아 "어느 방에 완료 공지를 남길지" 알 방법이 없다.
- 그래서 같은 조건으로 방 id만 먼저 조회한다.
- `chatRoomId is not null` — 채팅 연동 전에 만들어진 팟은 공지를 남길 방이 없어 뺀다.
- 두 조회·갱신 사이에 동시 접속이 끼어들면 완료 공지가 중복 발송될 수 있다. 자동완료 자체가 늦어도 손해가 없는 정리 작업이라 이 경합까지 막지 않는다(의도된 선택).

### findOpenPotsInBox

- native query 대신 JPQL인 이유 — MySQL의 `ST_Distance_Sphere`를 쓰면 h2로 도는 테스트에서 실행되지 않는다. 사각형 조건은 두 DB에서 같게 동작하고 `idx_pots_lat_lng`도 그대로 탄다.
- 내가 총대거나 이미 참여한 팟을 `not exists`로 빼는 이유 — 같은 카드가 위쪽 내 섹션과 아래쪽 전체 섹션에 두 번 뜨면 안 된다.
- 참여 이력 id를 자바로 가져와 `not in`에 넣지 않은 이유가 둘이다.
  - 이력에는 완료된 과거 팟까지 다 들어 있어 목록과 무관한 행을 읽게 된다.
  - `in ()`이 문법 오류라 이력이 비었을 때 더미 값을 끼워 넣는 우회가 필요했다.
- 상관 서브쿼리는 두 문제가 모두 없고 `uk_pot_members_pot_member (pot_id, member_id)` 인덱스를 그대로 탄다.
- `keyword`를 null 대신 빈 문자열로 받는 이유 — JPQL 파라미터의 null 타입 추론에 기대지 않기 위해서다.
- 호출부에서 `%`, `_`를 이스케이프해 넘기므로 쿼리에서는 `escape '\\'`만 선언한다.

### findMyLivePots

- 반경을 걸지 않는 이유 — 팟의 수령 위치는 내 등록 주소와 다를 수 있다(회사 근처 팟을 집 주소로 가입한 사람이 만들 수 있다). 300m를 걸면 내가 만든 팟이 내 목록에서 사라진다.
- 마감시간을 보지 않는 이유 — 참여자에게는 마감 후가 오히려 중요한 구간이다(주문·입금·수령). 이 섹션에서 사라지는 유일한 조건은 `DONE`이다.
- 참여 여부를 `exists`로 판정하는 이유(PR #63 리팩터링)
  - 참여 이력 id를 자바로 모아 `in`에 넘기면 완료된 과거 팟까지 전부 읽는다.
  - 이력이 쌓일수록 `in` 절이 길어져 쿼리 플랜이 흔들린다.
  - 걸러낼 대상은 어차피 살아 있는 팟뿐이므로 판정을 DB에 맡기는 쪽이 맞다.

## 7. PotService

### 상수의 근거

- `MIN_DEADLINE_MINUTES = 30` — 마감시간이 너무 촉박하면 아무도 참여하지 못한다. 최소 여유를 도메인 규칙으로 둔다.
- `KST` — 채팅 공지에 찍는 마감시간의 기준 시간대. 참여자는 전부 같은 동네에 있다.
- `SEARCH_RADIUS_METERS = 300` — 걸어가서 받아올 수 있는 거리로 기획에서 정한 값.
- `AUTO_COMPLETE_HOURS = 5`
  - 마감시간부터 재는 이유 — 그 이후가 주문·배달·수령 구간이다. 배달이 늦거나 총대가 버튼 누르기를 잊어도 이 시간이면 끝나 있다.
  - 너무 짧으면 아직 진행 중인 팟이 참여자 목록에서 사라져 총대 계좌를 찾을 길이 끊긴다.
- `MAX_RESULTS = Limit.of(100)` — 300m 반경이면 보통 수십 건이지만 밀집 지역에서 폭증했을 때 TEXT 설명까지 전부 직렬화되는 것을 막는다. 페이징이 붙으면 페이지 크기로 대체된다.

### create() — 채팅방을 같은 트랜잭션에서 만드는 이유

- 방 없는 팟이 남으면 복구 경로가 없다. 참여자가 "메뉴 전달하기"를 눌렀을 때 들어갈 방이 없고, 총대에게 방을 다시 만들 화면도 없다.
- 방 생성이 실패하면 팟도 만들어지지 않는 것이 낫다(총대는 다시 누르면 된다).
- 방 이름은 가게명이다 — 채팅 목록에서 어느 팟의 방인지 알아볼 수 있는 유일한 단서다.
- 만날 장소를 방 생성 요청에 함께 실어 보낸다 — 채팅 도메인이 배달팟을 몰라도 헤더에 장소를 띄울 수 있게, 채팅이 자체 보유하는 필드에 값만 얹어준다.
- 의존 방향은 **팟 → 채팅 단방향**을 유지한다. 채팅이 팟을 부르면 순환 참조가 되어 빈 생성 단계에서 실패한다.
  - 채팅방에서 팟 정보가 필요하면 `GET /api/pots/by-chat-room/{chatRoomId}`를 쓴다.
- 방을 만든 직후 가게 링크를 총대 명의 말풍선으로 올린다(PR #62) — 참여자가 들어왔을 때 무슨 가게인지 스크롤을 올리지 않고 바로 볼 수 있어야 한다.
  - 미리보기(제목·이미지·설명)는 여기서 가져오지 않는다. 방 생성 트랜잭션에 외부 HTTP를 얹으면 응답이 느려지고 그 호출 실패가 팟 생성을 막는다.
  - content에는 URL만 저장하고, 미리보기는 프론트가 방을 열람할 때 `POST /api/pots/store-name`으로 지연 조회한다.

### update() 의 세 겹 방어

- 참여자가 한 명이라도 들어오면 `POT_NOT_EDITABLE`로 막는다(이유는 2절 `hasOnlyHost()` 참고).
- 수정 폼을 열어 둔 사이 누군가 참여하는 경합은 `Pot.version` 낙관적 락이 막는다.
  - 참여 트랜잭션이 먼저 커밋되면 이 저장이 실패하고 `CONFLICT`로 응답된다.
  - 인원 검사만 두면 폼을 연 시점의 낡은 값으로 통과할 수 있다.
- 가게명·만날 장소가 바뀌면 연결된 채팅방의 이름·장소도 함께 맞춘다. 채팅방은 이 값들을 자체 컬럼으로 들고 있어(팟을 모른다) 여기서 밀어주지 않으면 옛 값이 남는다.
- 수정 결과를 돌려주지 않는 이유 — 상세를 만들려면 총대 닉네임·총대 횟수·참여자 목록까지 다시 긁어야 하는데 프론트는 저장 직후 목록/상세를 어차피 새로 조회한다.

### expandRecruitment() 를 update() 와 나눈 이유

- 규칙이 정반대다.
  - 전체 수정 — 참여자가 없을 때만 열리는 대신 무엇이든 바꿀 수 있다.
  - 모집 확장 — 참여자가 있어도 열리는 대신 늘리는 방향만 허용한다.
- 마감이 이미 지난 팟도 늘릴 수 있다. 정원이 안 차서 마감만 지난 팟을 다시 살리는 것이 이 기능의 주 용도다.
- `DONE`이면 막는다 — 끝난 팟을 되살리는 통로는 아니다.
- 값이 실제로 바뀐 경우에만 공지한다. 참여자는 이 두 값을 보고 들어왔으므로 조용히 바꾸면 안 되고, 같은 값 저장에 공지가 나가면 방이 시끄러워진다.
- `describeExpansion()`은 확장 **직전에** 뽑아야 이전 값을 읽을 수 있다.
- 공지의 마감시간을 KST 벽시계로 찍는 이유 — 저장된 `OffsetDateTime`을 그대로 문자열화하면 요청이 보낸 오프셋이 그대로 노출된다.

### findPots() — 홈 목록

- `hosted` / `joined` — 내가 속한 팟. 반경도 마감시간도 보지 않는다. 사라지는 조건은 나눔 완료뿐이다.
- `all` — 300m 이내, 마감 전, 정원 여유, 내가 속하지 않은 팟. 마감이 지나면 참여할 수 없으니 참여하지 않은 사람에게는 보일 이유가 없다.
- `readOnly`가 아닌 이유 — 맨 앞에서 방치된 팟(마감 + 5시간)을 일괄 `DONE`으로 전이시키고 각 채팅방에 완료 공지를 남긴다.
  - 이걸 안 하면 참여자 목록에 끝난 팟이 영구히 쌓이고, 참여자들은 방이 왜 조용해졌는지 알 방법이 없다.
- 세 섹션의 참여자를 한 번에 긁는다. 섹션별로 나눠 부르면 같은 쿼리가 세 번 나간다.
- `findOthersNearby()`는 쿼리가 이미 마감 임박순으로 정렬해 두었고 stream이 순서를 보존하므로 다시 정렬하지 않는다.

### join() — 참여 = 메뉴 전달

- 메뉴를 따로 보내는 API를 두지 않은 이유 — 화면이 한 버튼("총대에게 메뉴 전달하기")으로 둘을 동시에 한다. 나누면 참여는 됐는데 메뉴는 없는 중간 상태가 생긴다.
- 채팅 순서 — 멤버십 추가 → 입장 공지 → 메뉴 공지. 닉네임은 채팅이 몰라도 되게 여기서 조회해 완성된 문구로 넘긴다.
- **정원 초과 방어 두 겹**
  - `isFull()` 선검사로 정상 요청에 `POT_FULL`을 준다.
  - 두 사람이 같은 순간에 마지막 자리를 노렸을 때는 `Pot.version` 낙관적 락이 막는다(한쪽 커밋 실패 → `CONFLICT`).
  - 앞의 검사만 두면 둘 다 통과해 5/4가 된다.
- **중복 참여 방어 두 겹**
  - `existsByPotIdAndMemberId`는 정상 요청에 친절한 에러를 주기 위한 선검사다.
  - 같은 사람이 버튼을 두 번 빠르게 눌러 두 요청이 모두 통과한 경우의 정합성은 `pot_members` unique 제약이 보장한다.

### saveMembership() — 제약 위반 번역 (PR #60)

- 문제 상황
  1. 요청 A — `exists` = false
  2. 요청 B — `exists` = false
  3. 요청 A — INSERT 성공
  4. 요청 B — `uk_pot_members_pot_member` 위반
- `GlobalExceptionHandler`에 `DataIntegrityViolationException` 핸들러가 없어 `handleUnexpected`로 떨어졌다. 결과는 500 `INTERNAL_ERROR` + `log.error` + 스택트레이스.
- h2로 실제 재현했다 — `DataIntegrityViolationException` → `ConstraintViolationException` → `JdbcSQLIntegrityConstraintViolationException`.
- `save()` 한 줄만 `try`로 감싸고 unique 제약 위반만 `POT_ALREADY_JOINED`로 번역한다.
- **제약 이름으로 좁혀 판정하는 이유** — NOT NULL·FK 위반 같은 코드 버그까지 409로 포장하면 조용히 묻힌다. 그런 위반은 500으로 남아야 로그에서 발견된다.
- `contains`로 비교하는 이유 — DB마다 장식이 붙는다.
  - h2 — `PUBLIC.UK_POT_MEMBERS_POT_MEMBER INDEX ...`
  - MySQL — `pot_members.uk_pot_members_pot_member`
  - 대소문자도 갈려 무시하고 비교한다.
- `saveAndFlush`가 아니라 `save`인 이유 — `PotMember`의 PK가 `IDENTITY`다. Hibernate가 생성된 PK를 받아야 엔티티를 영속 상태로 만들 수 있어 INSERT가 이 호출에서 바로 실행된다. 별도 flush 없이 여기서 예외가 잡힌다.
- 예외를 잡은 뒤 DB 작업을 더 하지 않고 즉시 던지는 것이 중요하다. 제약 위반이 나면 Hibernate 세션이 오염돼 이후 flush 동작을 보장할 수 없다.

### findDetail() / findDetailByChatRoomId()

- 나눔 완료된 팟도 조회된다. 채팅방은 완료 후에도 남고 그 화면 상단이 이 API를 쓴다 — 여기서 막으면 완료된 팟의 채팅방 헤더가 비어버린다.
- `findDetailByChatRoomId`는 채팅방 헤더/배너가 potId 없이 roomId만 가진 경우의 역조회다. `Pot.chatRoomId`가 단방향이라 채팅 쪽에는 이 관계가 없다.

### leave()

- 총대는 완료 전엔 나갈 수 없다. 완료 전에 사라지면 정산 계좌 주인이 없어지고 남은 사람들이 주문을 이어받을 방법이 없다.
- 완료 전 총대에게는 대신 나눔 완료가 있다. 완료 후에는 총대도 참여자와 동일하게 나갈 수 있다.
- 채팅방 멤버십도 함께 제거한다 — 나간 뒤에도 방에 남아 메시지를 보고 보낼 수 있으면 안 된다.

### complete()

- 마감시간 전이라도 누를 수 있다. 정원이 다 차서 일찍 주문하고 받아 나눈 경우가 정상 흐름이고, 그때 마감까지 기다리게 하면 끝난 팟이 전체 목록에 계속 떠 있게 된다.
- 완료 공지는 `postSystemNoticeMessage`를 재사용한다 — 문구만 다른 센터 정렬 시스템 안내라 별도 타입을 만들지 않는다.

### leaveAllActivePots()

- 호출 전 `hasActiveHostedPot()`로 총대인 ACTIVE 팟이 없음을 이미 확인했다는 전제로 동작한다.
- 그래서 여기서 찾은 ACTIVE 팟은 전부 참여자로만 속한 팟이고, `leave()`를 그대로 재사용해도 `POT_HOST_CANNOT_LEAVE`에 걸리지 않는다.

### loadMembers() — 쿼리는 딱 두 번

- 참여 기록 전체 한 번, 닉네임 전체 한 번.
- 팟마다 참여자를 조회하면 목록 크기만큼(N+1), 참여자마다 회원을 조회하면 그 곱만큼 쿼리가 나간다.
- 회원이 지워진 참여 기록은 닉네임이 없다. 목록 전체를 죽이지 않게 빈 문자열로 흘린다.

### validateDeadline()

- `@Future`가 과거 시각은 걸러 주지만 "지금부터 30분"이라는 도메인 규칙은 Bean Validation으로 표현할 수 없어 주입받은 `Clock`으로 확인한다.
- `OffsetDateTime` 비교는 오프셋을 반영한 절대 시각(instant) 기준이라 서버 JVM 타임존이 UTC든 KST든 결과가 같다.
  - 벽시계 타입(`LocalDateTime`)으로 비교하면 UTC 서버에서 9시간 어긋나 이미 지난 마감이 통과한다.

## 8. DTO

### PotListRequest — 좌표를 요청에서 받지 않는 이유

- 회원가입 때 카카오맵으로 인증한 주소의 좌표를 서버가 직접 읽는다(화면 좌측 상단 "학동로 171").
- 클라이언트가 좌표를 보내게 두면 남의 동네 팟을 조회할 수 있다.
- 프론트가 좌표를 따로 들고 다녀야 해서 화면마다 어긋난다.
- `searchKeyword()`가 `%`, `_`를 이스케이프하는 이유
  - 파라미터 바인딩이라 SQL 인젝션은 아니다.
  - 이스케이프하지 않으면 사용자가 친 `%`가 LIKE 와일드카드로 해석돼 검색어 한 글자에 전체 목록이 나온다.
  - 역슬래시 자신을 먼저 이스케이프해야 `\%` 같은 입력이 깨지지 않는다.
  - 항상 non-null이며 빈 문자열이 "검색 없음"을 뜻한다.

### PotDetailResponse — 계좌를 참여자에게만 내리는 이유

- 상세 화면은 아직 참여하지 않은 사람에게도 열려 있다. 계좌를 항상 실으면 참여도 안 한 사람에게 계좌번호가 노출된다.
- 화면상으로도 계좌 배너는 채팅방(= 참여 후)에만 있다.
- 좌표를 함께 내리는 이유 — 총대의 수정 화면이 만날 장소를 다시 찍지 않고도 유지할 수 있어야 한다(PUT은 전체 값을 다시 보낸다).
  - 주소 문자열이 이미 내려가고 있으므로 위치 노출 수준은 달라지지 않는다.

### PotSummaryResponse — 목록 카드에서 뺀 것

- 가게 링크·정산 계좌는 없다.
- 목록은 참여 여부와 무관하게 열려 있으므로 계좌 같은 값이 섞이면 안 되고, 링크는 상세 화면에서만 쓴다.

### PotMemberResponse

- 프로필 이미지 컬럼이 없어 닉네임만 준다. 프론트는 첫 글자를 원 안에 그린다.
- 이미지가 생기면 필드 추가만 하면 된다 — 추가는 프론트 계약을 깨지 않는다.

### PotJoinRequest — 메뉴 없는 참여를 두지 않은 이유

- 총대가 주문을 넣으려면 참여자 메뉴가 반드시 있어야 한다.
- 참여만 해두고 메뉴를 안 낸 사람이 정원을 차지하면 총대가 최소주문금액을 채울 수 없다.
- 메뉴는 자유 텍스트다 — 가게마다 옵션 구조가 달라 서버가 구조화할 수 없고, 총대가 배달앱에 그대로 옮겨 적을 수 있으면 충분하다.
  - 예: "허니콤보 세트 (순살로 변경) + 콜라 제로 500ml"

### PotJoinResponse — chatRoomId 를 돌려주는 이유

- 참여하면 곧바로 채팅방으로 넘어가는 흐름이다. 없으면 프론트가 참여 직후 목록을 다시 조회해 방 번호를 찾아야 한다.
- 방은 팟 생성 시점에 이미 만들어져 있어 여기서는 그 id를 그대로 돌려준다.
- 참고 — "참여자를 방 멤버로 넣는 것은 아직 안 붙었다"는 옛 주석은 이번에 지웠다. `join()`이 `chatService.addMember()`를 호출하므로 사실이 아니다.

### PotListResponse — 세 배열로 나눠 내리는 이유

- 섹션마다 조회 조건이 실제로 다르다 — `hosted`/`joined`는 반경도 마감시간도 보지 않고, `all`은 반경 300m + 마감 전 + 정원 여유다.
- 한 배열로 내리면 이 차이를 표현할 수 없다.
- 같은 팟이 두 배열에 동시에 들어가는 일은 없다 — 총대면 `hosted`, 참여자면 `joined`, 둘 다 아니면 `all`.

### PotRecruitmentUpdateRequest 를 PotUpdateRequest 와 나눈 이유

- 두 경로의 허용 규칙이 반대다(7절 참고).
- 한 요청 타입으로 합치면 서버가 나머지 필드의 "안 바뀜"을 값 비교로 확인해야 한다.
  - 좌표 scale 차이, null/빈문자열 차이로 오탐이 난다.
- 규칙 두 벌이 한 메서드에 섞이는 것도 막는다.

### PotUpdateRequest 를 PotCreateRequest 와 합치지 않은 이유

- 지금은 필드가 같지만 두 계약이 앞으로 갈라질 자리가 있다.
- 수정은 참여자가 없을 때만 열리므로, 나중에 "참여자가 있어도 제목만 고치기"가 생기면 수정 쪽만 필드가 줄어든다.

### PotCreateResponse

- 생성 직후 화면 전환에 필요한 최소 정보만 담는다. 전체 필드는 상세 조회 API가 준다.

### PotCreateRequest / PotUpdateRequest

- `capacity`는 2~4명. 총대를 포함한 수다.
- `NonWhitespaceSize` — 제목 30자, 설명 200자는 **공백 제외** 기준이고 `absoluteMax`로 절대 길이도 함께 막는다(공백 폭탄 방어).
- `deadline`은 오프셋을 반드시 포함한다. 서버는 절대 시각으로 비교한다.
- `accountNumber`는 숫자와 하이픈만 8~30자.

## 10. 코드에 주석을 남기는 기준 (이번 정리에서 세운 규칙)

- 남긴다
  - 이 클래스·메서드가 **무엇을 하는지** 한 줄.
  - 코드만 봐서는 절대 알 수 없고, 모르면 **버그가 나는** 제약 한 줄.
    - 예: 벌크 UPDATE와 `complete()`가 같은 식을 복제하고 있다는 사실.
    - 예: 총대 행의 `menuContent`가 null이라는 사실.
    - 예: enum 이름이 프론트 계약이라는 사실.
- 옮긴다(이 문서로)
  - 대안을 왜 안 골랐는지, 트레이드오프, 기획 배경, 인프라 규모 판단.
- 절대 남기지 않는다
  - "~기능이 붙으면 쓰인다" 같은 미래 시제. 붙으면 곧바로 거짓이 된다.
  - 코드를 그대로 한국어로 옮긴 문장.
